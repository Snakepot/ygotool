# ygotool 技术路线

> 面向新读者/新会话：本文件说明项目的技术选型、分层架构、关键机制与演进方向。
> 配套文件：`workspace01/HANDOFF.md`（当前状态/待办）、`.claude/skills/ygotool/SKILL.md`（踩坑 29 条）、`agent-concepts-review.md`（概念与面试题；本机文档，未入库）。

## 一、目标与边界

- **定位**：基于 [ygocdb.com](https://ygocdb.com) 开放 API 的本地游戏王卡牌工具 + 查卡/裁定 Agent；**学习型项目**。
- **要解决的问题**：① 自然语言查卡/按效果找卡（要听懂"从手卡把水属性怪兽送去墓地的卡"这类话）；② 裁定问答（官方 FAQ + 效果原文 + 原则演绎，带来源引用、不确定分级）。
- **学习目标**：把 LLM 工程的 **AB 层**（推理参数 + 上下文工程）做成可调、可对比、可观测的模块——RAG 切分、embedding 选型、few-shot、temperature、token 预算、工具增强、trace、评测。
- **明确不做**：C 层权重微调（用闭源 API）；生产级高并发/多租户。
- **约束**：零依赖优先（标准库能跑）；成本敏感（不跑全量 FAQ 抓取）；尊重数据源（MD5 增量、FAQ 磁盘缓存、0.3s 限流）。

## 二、分层架构

```
用户自然语言（Web SSE / CLI）
        │
        ▼
CardAgent ── ReAct：GLM-5.2 原生 function-calling（真模型）/ 确定性管线（mock 兜底）
        │
        ├─ 工具层 ToolRuntime（工具增强降幻觉，答事实必经取数）
        │    search_card / get_card_detail / decode_card_fields
        │    search_by_action（动作本体，覆盖 cost+效果段）
        │    search_by_effect（效果体，结构化复合 keyword/source/target）
        │    search_effect_phrase（原文片段，最长连续匹配）
        │    search_by_series（系列卡名全量）
        │    rag_search（向量召回 FAQ/效果片段）
        │    get_limits / limit_status / get_release_date
        │
        ├─ 上下文层：原则库(P01/P02) + few-shot(cases.jsonl) + token 预算裁剪 + 别名归一化
        ▼
结构化检索层
        ├─ 卡池：sqlite cards 表（14295 张，cards.zip MD5 增量同步）
        ├─ PSCT 解析：①②分条、「才能发动」分离 cost/效果体、连词切动作单元、
        │            代词指代继承、否定/自肃过滤
        ├─ 动作本体 ontology：12 类动作 + SOURCES（区域）+ map_phrase_to_actions
        ├─ 特异度三档：★精确（限定一致+来源一致）/◆次精确（限定一致、来源更宽）/通用
        ├─ 来源区判定：取"动词之前"的片段（目的地如「墓地」不算来源）
        └─ RAG：embedding-3(1024 维) 索引 + 纯 Python 暴力余弦（effect / faq 两类 chunk）
        ▼
后端抽象（可热切）：LLM（GLM-5.2 / OpenAI 兼容 / mock）、Embedder（TF-IDF / embedding-3 / bge）
```

**数据流**：`cards.zip(MD5 增量) → sqlite cards → PSCT 解析/动作本体 → 工具检索 → 上下文装填 → LLM → trace/回答`

## 三、关键技术路线（每条：问题 → 选择 → 边界）

### 1. 从"词条匹配"到"PSCT 结构化 + 动作单元"
- **问题**：初版靠子串/关键词匹配，用户贴原文（如"把自己的手卡·场上1只怪兽解放才能发动"）找不到卡、枚举查询漏卡/误召。
- **选择**：按 PSCT 范式解析——①按「才能发动」剥离 cost 与效果体；②按连词（那之后/并且/此外/**或**）切动作单元；③每个单元抽 动作/来源/目标；④否定词（不能/无法/不用/无需…）跳过；⑤代词句（那只怪兽…）继承同条款"区域+数量+「目标」"声明的来源。
- **边界**：半精确（§13）——身份类（种族/类型/星级）位掩码精确，动作/原因类靠文本与 FAQ，非 100%。

### 2. 特异度优先（P03）+ 三档分级
- **问题**：结果只"包含"不够——用户要的是"明确限定条件"的卡（如"限定 3 星的基路伯"），泛化卡应靠后/置入通用组。
- **选择**：`_query_modifiers` 抽限定词（等级/属性/种族/怪兽类型）→ 每条结果按来源区集合与限定词命中算档位：★精确 / ◆次精确 / 通用；精确组列全（名单 ≤60 张时全量渲染，超过 60 才按 30/15/10 截断），渲染分组，提示词要求"先精确、再补一句次精确、再通用"。
- **边界**：限定词词典需人工扩充（别名表 + `_query_modifiers`）。

### 3. 来源区精度（"手卡·卡组/手卡·场上"）
- **问题**：① 查询里的「墓地」是目的地，却被当来源；②"手卡·卡组""手卡·场上（表侧表示）"离动词 9–23 字，8 字窗口匹配不到 → 波塞德拉深渊/轰海皇漏召。
- **选择**：`source_zones_from_phrase`/`first_verb_pos`（动词前片段才是来源）；`tag_action_units` 记录每单元 `zones`；手牌送墓窗口放宽到 20 字并新增组合来源句式；连词表加「或/或者」防跨动作串味。
- **边界**：组合来源（手卡·卡组）判定为"次精确"而非精确，语义上与用户直觉一致。

### 4. 查询别名词（自然语言冗余，additive）
- **问题**：用户说法多样（手牌/手卡/手札；等级3/3星；检索/堆墓/丢手/苏生/自跳；白怪/黑怪…），硬编码会漂。
- **选择**：`agent/data/aliases.md` 可编辑别名表（literal + regex，`⏸` 标记暂不纳入的模糊黑话），解析后**只扩写匹配候选、不改原文**；接入 `_normalize_query`，所有搜索入口统一归一化。
- **边界**：⏸ 项（康/擦/炸/除/飞/阻抗/蓝怪/陀螺）定义模糊，待用户定边界再启用；字段清单未拆简称。

### 5. 找卡路由：动作检索 vs 效果体检索
- **问题**：模型做"精确找卡"时爱用 `search_by_effect`，但**它只搜效果体**（「才能发动」之后），cost 型卡（如基路伯的送墓在 cost）天然漏掉。
- **选择**：找卡**强制走 `search_by_action`**（不传 reason 时 cost+效果段都搜，含特异度分组）；`search_by_effect` 明确标注"只效果体、不含 cost"，仅用于效果体复合检索。
- **边界**：裁定问题里的 cost≠效果 判断仍由原则+FAQ 承担（工具不替模型下结论）。

### 6. ReAct 编排与熔断
- **选择**：真模型走原生 function-calling 多轮；`MAX_ITERS=4` + `MAX_TOOL_CALLS=10`；首轮路由关 thinking（秒回）、拿到工具结果后开 thinking（ruling 深思）；**轮数耗尽强制一次无 tools 收尾**，避免"工具调用达上限"空答案；提示词规定"枚举只调一次、不逐卡 get_card_detail"。
- **边界**：mock 后端不支持原生 tool-calling，走确定性管线兜底（trace 结构不变）。

### 7. RAG：双轨 + 可切后端
- **双轨**：原则（成文法，可推广）管演绎；FAQ（案例法，不可还原）管兜底；两者都喂推理模型。
- **检索**：FAQ 日文原文 + 效果体两种 chunk；embedding-3 跨语言（TF-IDF 跨语言召回为 0，仅作零依赖兜底）；sqlite 存 float32 + 暴力余弦（卡池 ~1.5 万，不需要 sqlite-vec）。
- **边界**：当前索引为小样例（effect 256 卡 / faq 2 卡）；全量 `build-index --all` 是成本项，待用户拍板。

### 8. Token 预算与上下文管理
- 优先级裁剪：system > 当前问题 > 历史（最新优先）> few-shot > 检索 chunk；reserve_completion 给输出留预算；大名单只给"总数+样例"，完整名单走前端。
- 推理模型（GLM-5.2）：`reasoning_content` 算 completion token → max_tokens 8192、任务级 thinking 开关。

### 9. 可观测与评测
- **trace**：每次问答记录工具链/迭代轮数/token 用量，调参可复盘。
- **评测 harness**（`eval/run.py`）：判例集 `cases.jsonl`（q + golden ruling + must_cite）→ LLM-as-judge 正确率 + must_cite 引用率 → `result.csv`。
- **已知问题**：C01/C02 偏"开卷"（答案写在 principles.md 正例里）；LLM 与 judge 有方差；判例数少（7 条）；C23 口径已按用户裁定改为宽口径（精确/次精确两段输出），C24 引用偶尔漏（模型方差）。
- **对策**：判例去开卷化（同原则换卡/措辞/未确认旧卡）、扩判例、多跑取平均。

## 四、一次问答的数据流

1. 前端 `POST /api/chat`（SSE 流式，5s 心跳保活）。
2. `CardAgent.ask_stream` → `_react_stream`：system（人设+任务+原则+工具规约）+ few-shot（cases）+ 多轮历史 + 问题。
3. 首轮关 thinking 选工具（search_by_action / rag_search / get_card_detail…）；工具在进程内访问 sqlite/在线 FAQ。
4. 工具结果以 `tool` 角色消息回灌；后续轮开 thinking 综合；撞上限/轮数耗尽 → 强制无 tools 收尾。
5. 流式输出 content/usage；trace 事件先发给前端（工具链/迭代数/token）。
6. 前端 Markdown 渲染、思考折叠、`卡牌#id` 可点开详情。

## 六、当前边界与已知缺口

1. **P06 文本提及≠执行**：「超再生能力」这类只"统计/引用"他处动作的卡仍会被误召 → 需句式过滤（未做）。
2. **本体覆盖**：仪式/融合/同调/超量/连接/灵摆召唤、覆盖/放置、反转召唤、回收等动作缺失；句式模板需按用户笔记补全。
3. **别名 ⏸ 项**：康/擦/炸/除/飞/阻抗/蓝怪/陀螺等定义模糊，需用户定边界。
4. **索引规模**：只覆盖 256 卡（effect）+ 2 卡（faq）的小样例；跨卡裁定召回仍弱；全量索引是成本项。
5. **评测**：7 条、小样本、C01/C02 开卷、LLM 方差 → 数字只能作趋势参考。
6. **deck 任务**：依赖 RAG 主题卡召回，仍偏弱。

## 八、设计原则（取舍依据）

- **零依赖优先**：标准库能跑；额外依赖放 extras；mock 兜底无 Key 可跑。
- **对上层透明**：LLM/Embedder 统一接口，换后端只改构造。
- **工具增强降幻觉**：答卡牌信息必经工具取数。
- **trace 全程可见**：调参与复盘的基础。
- **成本敏感**：embedding/推理 token 都算钱，全量索引与思考开关按需。
- **领域知识由用户主导**：原则库/判例/别名/黑话的 golden 由用户（裁定行家）定，代码只负责机制。
- **单一交接入口**：`workspace01/HANDOFF.md`；本文件补充"为什么这么做"，不代替它。
